# 1. 产品定位与 V1 边界

目标体验：默认自主运行、正常状态不打扰；发生预算超限、支付异常、缺货或断粮风险时，再把需要用户决策的事情呈现在首屏。

| **包含（V1）** | **不包含（V1）** |
|----|----|
| 单宠（七仔）＋单一常用狗粮 SKU；库存估算与人工修正 | 多宠物、多粮混用、称重硬件自动感知 |

| 计算耗尽日与下单日；模拟店商品、配送假设与订单 | 真实商家采购、保证配送时效 |

# 3. 信息架构：主页极简，控制项下沉

## 3.1 正常首屏（固定骨架与终端方向）

主设计目标：手机竖屏优先（设计基准 390×844 CSS px，移动端响应式适配）；聊天从底部展开，日期格可横向滚动。桌面浏览器仅用居中单列手机宽度预览，不做电脑两栏主界面。演示录屏采用手机竖屏。

顶部：Replenish 品牌 + 小型 Agent 状态入口（可点击进入控制页，不占用首屏主视觉）。

核心区：一个带名字和动作的动态衬线大标题；下方常驻一行有依据的 Agent 理由。

主体：七仔头像与名称组成可点击的宠物入口，下方为连续日期格（默认 7～8 格，可横向滚动或自动调整起点）。首屏不显示估算库存克数、每日／每顿喂食量或其他喂食摘要；这些信息在点击七仔后进入详情层查看。

底部：常驻自然语言输入栏；点击展开底部聊天层，不把聊天记录永久铺在主页。

二级：七仔详情（估算库存、每日用量、每顿克数、库存校准与计划编辑）、预算详情、Autopilot/支付授权、最近活动、三节点计划详情、订单详情。正常首屏不再放“Everything is taken care of”大卡、预算概览卡及活动列表。

## 3.2 日期格与计划详情分工

首屏连续日期格承载日期节奏，标记“计划下单”“预计送达”“预计耗尽”的不同状态；尚未执行的下单日严禁显示完成对勾。点击有事件的日期格进入计划详情。

计划详情采用三节点：Order → Expected delivery → Estimated runout，并展示计算依据（估算库存、每日用量、商店配送时长及安全缓冲）。计划节点与实际订单物流状态严格分离。

# 4. 六种主状态与显示优先级

| **状态** | **首屏变化 / 关键操作** |
|----|----|
| ① Scheduled | 保持简洁大标题、理由、七仔、日期格与输入栏；不主动发送正常提醒。 |
| ② Preparing | 标题换为执行中；主要展示当前任务步骤，完成才打勾；避免并发创建订单。 |
| ③ Ordered | 显示已确认订单及预计配送；订单和支付详情进入二级；仅确认成功后才宣告成功。 |

| ⑤ Failed / Reconciling | 支付已知失败显示可恢复路径；支付结果未知单独显示核对中，不能盲重试或断言未扣款。 |

页面优先级：断粮风险与需要批准 \> 订单执行异常 \> 任务执行中 \> 下单成功 \> Scheduled。不要为每种状态改变导航结构。

# 6. 喂食指令、库存预测与补货策略（D02）

## 6.1 三类喂食事件

| **意图** | **示例** | **更新方式** |
|----|----|----|
| 永久修改 | 以后每顿少喂 10g | 更新默认每顿 75→65g、每日 150→130g；立即重算耗尽日与候选下单日，按第 6.2 节阈值决定是否更新计划 |
| 临时少喂 / 跳过 | 明天晚饭少喂 10g / 明天晚饭不喂 | 创建指定餐次的临时事件，更新预测与候选下单日；按第 6.2 节同一阈值判断 |
| 实际消耗反馈 | 今天午饭只吃了一半 | 记录实际喂食或耗用；区分袋内库存与已取出的剩粮，必要时询问 |

模糊输入如“少喂一点”“今天不想吃”应追问餐次、克数或是否仅描述食欲；不能自动转成长期喂食方案。系统不据此做诊断。

2026-11-01 主人验收补充：聊天中的长期饭量修改必须说明每天总量或每顿用量；缺少范围时先追问。每日总量增加或减少达到30%时，先展示原值和目标，明确“尚未修改”，不更新饭量或补货计划。完整绝对目标确认（如 `确认：每天总共85g` 或 `确认：每天两顿，每顿85g`）才执行，并保留修改回执和撤销；单独“好的／第二个”不执行。30%是防误操作阈值，不是营养判断。小幅明确修改仍直接保存。

计划详情中的计划下单、预计送达、预计耗尽只显示家庭时区中的年月日；后台保留准确时间计算，Agent运行记录仍显示时分秒。此次补充不调整页面入口。

## 6.2 计算与调整时机

每日基准消耗 = 每日餐数 × 每餐克数；当前库存估算 = 上次校准库存 − 已发生实际取粮量 + 已确认入库量。预测应结合具体餐次、临时事件与时区，而不只用简单整天取整。

目标送达时间应早于预计耗尽时间并留安全缓冲；计划下单时间由预计配送时长、商家截单/非营业日等约束倒推。日期格与详情使用同一结果来源。

统一阈值（永久与临时调整同一规则）：每次喂食量或指定餐次发生变化，都立即重算预计耗尽时间和「候选下单时间」。候选下单时间与当前已保存计划下单时间的绝对差值 ≥24 小时，且计划仍可修改，才更新已保存的下单计划；差值 \<24 小时则保持原下单日，但同步更新库存/耗尽预测，并反馈“已判断，计划不变”。提前断粮风险例外按下文处理。

24 小时按两个带时区的时间戳计算，不以跨越零点或“日期显示变了一格”代替判断；更新后以用户本地日期渲染日期格，保存候选时间、阈值判断结果和前后值，避免来回波动。每次新事件以上一次已保存计划为基准重新比较。

唯一阈值例外：若当前计划下估计到货时间＋安全缓冲晚于预计耗尽时间（存在提前断粮风险），可不受 24 小时阈值限制，立即重新评估并适当提前下单；若即使提前也无法规避断粮，需标记风险、提示主人处理，不能默认为已经解决。风险例外仅用于提前，不用于无故推迟。

已经确认付款的订单不得因喂食计划改变而自动撤销；支付处理中、已提交或不允许更改的订单不回写旧订单日期，只更新后续预测并说明当前订单状态。

演示对照：初始估算库存 1200g，每天 2 顿 ×75g＝150g/天，静态估算可食用 8 天。①“以后每顿少喂 10g”：新用量 65g×2＝130g/天，1200÷130≈9.23 天，比原来约延后 1.23 天（29.54 小时）；在固定配送、缓冲和无截单/营业日跳变的演示条件下，候选下单时间推迟 ≥24 小时 → 必须更新计划。②“明天晚饭不喂”：少取粮 75g，相当于原消耗速率下约 0.5 天（12 小时），候选下单时间推迟 \<24 小时 → 不改计划。首页显示“Noted. Qizai skips dinner tomorrow.”，理由显示“That’s half a day of food, so the reorder date stays the same.”；聊天层同步解释并记录该判断。

演示验收数据固定条件：以 1200g 为库存起点；不发生额外取粮、补库存或其他临时事件；同一模拟商店、稳定的配送时长/安全缓冲、相同的下单时刻及无营业日跳变。必须校验实际产生的 candidateOrderAt 与 plannedOrderAt 差值；若商店日历使差值变化，应调整演示时点/测试夹具，不得硬编码“改期成功”。

库存估算失真、临时用量显著变化或出现“可能在送达前吃完”时，优先请求库存校准、显示风险，而非展示虚假的精确天数。

# 7. 预算审批与 PayPal Sandbox 规则（D01）

## 7.1 预算闸门与一次性审批

自动支付必须同时满足：SKU/商家规则符合、自动付款授权有效、订单总价（税费/运费已含）≤\$50、本月已结算＋已承诺＋本次订单≤\$120、无冲突或重复订单。规则由后端确定性执行，大模型不能单独决定扣款。

双超限案例：本月已支出 \$90，待购 8kg、\$72.99；单笔超限 \$22.99，购买后月累计 \$162.99，超出月限 \$42.99。审批卡必须同时说明两条超限原因。

批准仅适用于当前草案的 SKU、店铺、币种、含税运费总价、有效期及订单 ID；重新计算价格或更换商品时旧批准失效。按钮点击后禁用重复提交，回执未知进入核对中。

2026-10-30 评审加固：审批提交必须带页面收到的 `approvalSnapshot` 和 `expectedTotalCents`。服务端快照指纹绑定订单 ID、SKU、店铺、币种、总价和袋重，任一项变化均不发起付款，刷新当前订单要求重新查看和批准；核验通过的指纹写入审批记录。它是内容一致性凭据，不代替用户批准或付款授权。

月预算口径：已结算按家庭时区的实际付款月份计入；待审批、付款准备中、支付核查中的未结清订单跨月继续预留，不按创建月份释放。核实付款后移除预留并按真实付款月份入账；明确拒绝或确定失败释放未付预留。核查未决不能当作失败。详情页的本月余额＝月上限－本月已结算－所有未结清预留。

## 7.2 测试支付真实边界

Demo：库存、商家商品目录、模拟商店订单为测试数据；预算判断、状态机、日志与库存计算均以真实业务代码运行；支付使用已具备的 PayPal Sandbox 集成方式发起真实测试交易并验证结果。

PayPal connected ≠ 自动扣款已授权。只有当前 Sandbox 商户能力、用户授权和实际 API 流程允许时，才可演示免交互自动支付；否则明确展示必要的授权动作，不伪造 Vault 或自动支付能力。模型不接触令牌；敏感数据只存受保护后端。

调用模拟商店与支付服务时使用幂等键；网络超时或支付未知先查询交易和草案/订单，再决定重试。Sandbox 支付成功不代表现实商品已采购或寄出。

# 8. 状态机、失败恢复与通知策略

定时暂停补充（2026-10-30）：聊天可指定恢复日期，按家庭时区该日 00:00 保存 UTC 恢复时刻，在到期后的首次后台检查恢复。默认检查周期 15 分钟；暂停购买不停止库存估算或支付核对。回复、首页提示与控制页显示期限和时区。无年份日期使用家庭当前年份；过去、无效日期先澄清，不擅自推断下一年或忽略用户要求的具体钟点。当前只支持日期级暂停。“下周”表示家庭当前日期加 7 天。手动保持暂停、提前恢复、演示重置清除期限；新日期替换旧期限。恢复时重算当前库存和计划，继续检查当前授权、vault、单笔/月预算及已有订单。保留已付款订单和未知支付，不能补发重复购买；常规恢复记入活动，不新增推送事件。旧数据中没有期限的暂停仍为手动恢复。

| **当前** | **事件** | **下一状态 / 反馈** |
|----|----|----|
| Scheduled | 到达下单时机 | Preparing |
| Preparing | 预算超限 | Awaiting approval；不发起付款 |
| Awaiting approval | 一次性批准＋再次校验通过 | Preparing；调用 Sandbox 支付 |
| Preparing | 交易结果不明 | Reconciling；查询交易，不允许重复扣款 |
| Preparing | Sandbox 支付确认且模拟订单确认 | Ordered |
| Preparing | 明确失败／缺货 | Failed；给重试、替代店或手动处理入口 |
| Ordered | 模拟物流状态更新 | Shipped → Delivered（不得提前将预计送达当成已送达） |
| 自动购买可用状态 | 用户暂停 | Paused；不再启动新购买，保留监测 |

通知分级（2026-10-30 经主人确认补充）：Scheduled 正常计算与计划微调不推送；审批待处理、已确认付款、明确支付失败、支付结果未知和断粮风险允许经主人授权后发送 Telegram 关键事件通知，同时保留网页处理入口。消息只跳转网页，不直接批准或付款。缺货仅在有可信商家事件时通知，当前模拟商店流程不伪造缺货。V1 不使用邮件通知。配置和可靠性边界见 [PayPal 与通知说明](paypal-integration.md#notifications)。

当剩余可用粮量不能覆盖预计配送周期＋安全缓冲，需主动升级风险。通知关闭时依然保留 App 内显著警示。

# 9. 首次配置与 Demo 边界（D01）

完整产品必须设计 Onboarding：宠物资料 → 狗粮 SKU／规格／当前估算库存 → 餐次与克数 → 配送和缓冲 → 单笔/月度预算 → PayPal 连接及适用的自动支付授权 → 确认。此流程保留于产品设计，但不是首轮 Demo 的重点。

Demo 可预置七仔、狗粮、当前库存及商店数据；不可虚构完成的 PayPal 授权或已成功支付。演示环境需清楚标识 Sandbox／示例商店。

## 9.1 P0：PayPal 连接与预算授权（独立单屏）

从 P2 完整 Onboarding 中独立提前一屏，纳入 P0：展示 Sandbox 标识、PayPal 连接/授权状态、连接按钮、单笔自动支付上限（默认 \$50）、每月累计上限（默认 \$120）、确认授权按钮、暂停自动购买入口。先完成适用的 PayPal 测试授权，再在本系统保存用户预算规则；连接成功但不满足自动扣款授权时必须显示“尚未授权自动支付”，不得显示为 Enabled。

关键交互：①未连接→点击 Connect PayPal→走当前 Sandbox 支持的实际授权流程；②返回后端验证结果→授权成功才可启用 Autopilot；③用户编辑两个额度→校验币种、正数和限额→保存并即时适用于新订单；④授权失败/取消→停留在未启用状态并可重试；⑤暂停后不再创建新支付请求，已提交订单按原状态继续跟踪。

测试安全约束：浏览器不保存 Vault token/敏感密钥；后端校验授权及预算；PayPal Sandbox 付款结果必须从真实接口/回执核验。若当前集成方式不支持后台免交互扣款，则明确展示所需用户确认步骤，不能将其伪装为静默自动付款。

# 11. Demo 三段演示及验收标准

| **演示段落** | **触发与观测结果** | **最低验收** |
|----|----|----|
| A. 聊天改饭量 | 预置库存 1200g；输入“以后每顿少喂10g” → 75→65、150→130；真实重算。 | 确认可食用时间约 8→9.23 天；有可撤销记录，非文本假回复。 |

| C. 超额审批与支付 | 触发模拟店超额报价 → 展示双预算超限 → 用户批准 → Sandbox 支付 → 订单更新 | 未批准不扣款；后端校验、交易回执和日志可核验 |

开发顺序：P0＝手机竖屏 Scheduled 首页与日期格、Chat 底层、每次重算＋24h 变更阈值、已判断不变反馈、审批卡、单笔/月度预算校验、独立 PayPal Sandbox 连接＋额度授权屏、真实 Sandbox 支付及最小订单状态；P1＝执行中/成功/失败的简洁反馈、预算/控制/活动详情；P2＝除 PayPal 授权屏外的完整首次配置及复杂比价。

基础验收：①手机竖屏 390×844 为主，首屏不出现估算库存克数及喂食摘要，点击七仔可查；②演示初始库存固定 1200g，150g/天≈8天，130g/天≈9.23天；③永久少喂10g案例改期（固定演示条件下 Δ≈29.54h），跳过75g晚饭案例不改期（Δ≈12h），两例均从一致基线独立测试；④常规 Scheduled 零推送；⑤日期格不把计划节点标为已完成；⑥所有喂食调整都重算，\|Δ候选下单时间\|≥24h 才更新，断粮风险可例外提前；⑦首页/聊天均提供“已判断、计划不变”反馈；⑧PayPal 授权屏走真实 Sandbox，单笔 \$50/月 \$120 规则有效；⑨支付未知不盲重试，已付款订单不自动撤销；⑩暂停不发新购买，无邮件通知。
